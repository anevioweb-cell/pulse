# Caching

Where each kind of data lives, how long it is trusted, and what replaces it. Values come from `src/features/telemetry/config.ts` (`STORE`, `QUERY_POLICY`, `API`) and `src/shared/api/config.ts` (`QUERY_DEFAULTS`, `RETRY`, `PERSISTENCE`). The reasoning per resource is in [ADR 0016](adr/0016-cache-policy-and-staleness.md), persistence is in [ADR 0017](adr/0017-indexeddb-persistence.md) and [ADR 0018](adr/0018-demo-alert-rules-persistence.md), and the service worker is in [ADR 0020](adr/0020-service-worker-and-pwa.md).

## Two kinds of data, two stores

| Live data                                                    | Server data                                                        |
| ------------------------------------------------------------ | ------------------------------------------------------------------ |
| Readings pushed over WebSocket (or by the simulator worker)  | Resources fetched on request through `TelemetryApi` (REST or Demo) |
| Zustand store (latest state) + typed-array ring buffers      | TanStack Query cache (memory), optionally IndexedDB                |
| Written by `TelemetryService`, at most one publish per frame | Written by TanStack Query from `queryFn` results                   |
| Read with `live.ts` hooks                                    | Read with `useDevices`, `useHistoricalReadings`, and so on         |

The boundary is strict, in both directions:

- Live readings never go into the Query cache, and no hook in `api/hooks.ts` reads the Zustand store.
- Server responses are never copied into the Zustand store or the ring buffers.

A chart that shows "the last 24 hours up to now" combines both: the historical range from the Query cache, and the most recent samples from the ring buffer. A range that reaches "now" is refetched at most every 30 seconds, because the ring buffer covers the gap in between (see readings below). Combining the two in one chart is Phase 5 work.

## Policy per data type

"Fresh" means TanStack serves the cached value without refetching. "gcTime" is how long an entry stays in memory after the last component using it unmounts. Only entries still in memory are written to IndexedDB, so gcTime also bounds persistence.

The 24 h gcTime for the device list and alert rules is long on purpose: they are small, and keeping them lets the persisted snapshot include them even when no screen shows them.

## Service worker

The service worker only makes the **app shell** available offline. It never caches data (ADR 0020).

- **Precache:**
  - the hashed JS and CSS bundles, `index.html`, the three fonts, `theme-init.js`, the favicon, the icons and the manifest: 15 entries, 526.64 KiB as reported by vite-plugin-pwa (performance.md);
  - the lazily loaded registration chunks (vite-plugin-pwa's register code and workbox-window) are included.
- **Navigations:** they fall back to the cached `index.html`, so deep links work offline, except paths under `/api`, which always go to the network.
- **No runtime caching:** fetches that are not precached (REST, cross-origin, anything new) go straight to the network. WebSockets are never seen by a service worker.

**Update policy.** A new build produces a new `sw.js`. The browser installs it in the background, and it **waits**:

- `UpdateAvailableBanner` offers "Reload now" or "Later".
- "Reload now" sends `SKIP_WAITING` to the waiting worker, and the page reloads when the new worker takes control.
- "Later" hides the banner until the next version. The old version keeps serving until every tab using it is closed.

Nothing reloads by itself, because a reload would clear the in-memory live buffers.

## Offline behavior

| Situation                               | Demo Mode                                                                                                                                                                                   | Live Mode                                                                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| App shell, after one online visit       | Loads from the precache                                                                                                                                                                     | Loads from the precache                                                                                                            |
| App shell, first visit offline          | Does not load (nothing cached yet)                                                                                                                                                          | Does not load                                                                                                                      |
| Live data                               | Keeps running: the simulator runs in a worker in the browser                                                                                                                                | Stops. The transport reconnects with backoff, and connectivity is `offline`, or `degraded` while reconnecting                      |
| Server data (devices, readings, alerts) | Keeps working: `DemoTelemetryApi` needs no network (`requiresNetwork: false`), so its QueryClient uses `networkMode: 'always'` and fetches are never paused. Prefetching also runs offline. | Cached and restored entries are shown. Refetches pause until the browser is back online, then stale queries refetch                |
| Alert-rule mutations                    | Fail at once with `offline` and roll back while the browser reports offline (the same rule as Live, so behavior does not depend on the mode)                                                | Fail at once with `offline` and roll back. No queue (ADR 0019)                                                                     |
| Banner                                  | "You are offline", with the demo body ("Demo data keeps running")                                                                                                                           | "You are offline", with the live body; "Connection problems" when online but the live connection is reconnecting, failed or silent |

`navigator.onLine` reporting `true` does not prove connectivity (a captive portal also reports true). The connectivity model (`features/telemetry/connectivity`) therefore also uses the live transport's state and the time of the last message.

### Failures and retries

Every query fails with `ApiError`. Network errors, timeouts, 5xx and 429 are retried up to 3 times, with a backoff of 500 ms, 1 s and 2 s (capped at 8 s). 4xx and validation errors are never retried, because retrying cannot fix them. Mutations are never retried automatically, because a retried POST could create a rule twice.

## Keys and invalidation

Keys are hierarchical, and the mode is the second level (`api/query-keys.ts`):

```
['telemetry', mode]                                   everything for one mode
['telemetry', mode, 'devices', 'list']
['telemetry', mode, 'devices', 'detail', id]
['telemetry', mode, 'devices', 'readings', id, {metric, from, to, maxPoints}]
['telemetry', mode, 'alerts', 'rules']
['telemetry', mode, 'alerts', 'history', {from, to, limit}]
```

- Demo and live data can never share an entry, so switching modes needs no cache clearing for correctness.
- Every level is a prefix of the next, so `invalidateQueries({ queryKey: ['telemetry', mode, 'devices', 'readings', id] })` drops every range of one device, and `['telemetry', mode, 'alerts']` covers rules and history together.

The alert-rule mutations are the only application code that invalidates: `['telemetry', mode, 'alerts']`, once the last pending rule mutation settles (ADR 0019).

## Known limitations

- **One gcTime for every readings range.** `gcTime` is a plain number fixed when the query is created: TanStack's types allow a function for `staleTime` (evaluated whenever freshness is checked) but not for `gcTime`. A range that reaches "now" today is in the past an hour later, so a gcTime chosen at creation would be wrong for it. All ranges therefore share one value, 30 minutes, which suits past ranges (zooming back and forth) and is longer than a growing range needs.
- **The debounce can postpone writes.** Persistence is debounced, not throttled. A cache that changes at least once a second is not written until it settles. With the policies above, the fastest refetch is every 15 s, so the cache does settle in practice. A tab closed less than 1 s after the last change loses that change, and the next visit refetches it.
- **Little is wired into the app yet.** `AppProviders` creates the QueryClient and shows the status banners, and `main.tsx` registers the service worker. But no screen calls the data hooks, and `setupTelemetryPersistence` is not called at startup. Phase 5 wires them. The policies above are covered by unit tests (`api/hooks.test.tsx`, `api/persistence.test.ts`, `api/rule-mutations.test.ts`).
- **Optimistic state can be persisted.** If the tab closes while a rule mutation is in flight, the debounced write may store the optimistic list. The next load revalidates rules on mount (ADR 0018), so it is corrected within one request.

## Resolved limitations

- **Demo queries paused offline (resolved in Phase 5A).** Queries used TanStack's default `online` network mode, so in Demo Mode new fetches waited for the browser to report online, although nothing leaves the browser. Each `TelemetryApi` now says whether it needs the network (`requiresNetwork`), and `createTelemetryQueryClient(api)` sets the queries' `networkMode` from it: `always` for `DemoTelemetryApi`, `online` for `HttpTelemetryApi`. No query sets its own mode. Tested in `api/query-client.test.tsx`: with `onlineManager` offline, Demo queries resolve and Live queries stay `paused` until it is back online. Alert-rule mutations are unchanged: they fail at once offline in both modes (ADR 0019).
